# 클로드코드 코딩 세션에서의 컨텍스트 엔지니어링

일반적인 컨텍스트 엔지니어링과 클로드코드로 코딩할 때의 컨텍스트 엔지니어링은 다릅니다.

---

## 클로드코드 코딩 세션에서의 컨텍스트는 뭔가?

클로드코드가 코딩할 때 컨텍스트가 어떻게 조립되는지부터 봐야 합니다:

```
┌─ 고정 (제어 불가) ──────────────────────────┐
│  System Prompt     클로드코드 내장 지시문      │
│  Tool Definitions  Read, Edit, Grep 등 도구   │
└────────────────────────────────────────────────┘
┌─ 반고정 (제어 가능) ───────────────────────────┐
│  CLAUDE.md         프로젝트 지시문              │
└────────────────────────────────────────────────┘
┌─ 동적 (세션 중 누적) ─────────────────────────┐
│  Conversation      사용자 요청 + Claude 응답    │
│  Tool Outputs      파일 내용, grep 결과, bash  │ ← 전체의 80%+
└────────────────────────────────────────────────┘
```

플러그인이 제어할 수 있는 영역은 "반고정"과 "동적"에서의 신호 품질입니다.

---

## 클로드코드 코딩 세션의 생명주기

```
사용자: "인증 기능 추가해줘"
         │
         ▼
    ① 탐색 (Discovery)          ← 컨텍스트 소비의 대부분
       Glob → 파일 찾기
       Grep → 패턴 검색
       Read → 파일 읽기
         │
         ▼
    ② 이해 (Comprehension)       ← 축적된 컨텍스트의 품질에 의존
       구조 파악, 패턴 추론
       기존 컨벤션 학습
         │
         ▼
    ③ 실행 (Action)
       Edit/Write 코드 수정
         │
         ▼
    ④ 검증 (Verification)        ← 또 컨텍스트 소비
       Bash → 테스트 실행
       Read → 결과 확인
```

가장 큰 컨텍스트 낭비는 **①번 탐색 단계**에서 발생합니다. 파일을 못 찾아서 grep를 5번 하고, 찾은 파일이 500줄인데 필요한 건 10줄이고, 패턴을 몰라서 비슷한 파일을 3개 더 읽어야 하고...

> **클로드코드에서의 좋은 컨텍스트 엔지니어링 = 탐색 오버헤드를 최소화하면서 탐색 정확도를 극대화하는 것**

---

## 5가지 차원

### 1. Navigability — Claude가 원하는 것을 빠르게 찾을 수 있는가?

```
나쁨:                              좋음:
src/                               src/
  utils.ts (2000줄, 모든 것)         auth/
  helpers.ts (뭐가 들었는지?)          controller.ts
  index.ts                            middleware.ts
  types.ts (모든 타입)                 types.ts
                                    payments/
                                      controller.ts
                                      types.ts
```

Claude는 IDE가 없습니다. `Glob("**/auth*")` 이나 `Grep("authentication")` 으로 찾습니다. 파일명이 예측 가능하면 한 번의 검색으로 도달합니다. 예측 불가능하면 여러 번 검색하고, 매번 결과가 컨텍스트에 쌓입니다.

### 2. Readability — 파일을 읽었을 때 신호가 높은가?

```
나쁨: utils.ts (800줄) → Claude가 다 읽음 → 필요한 건 formatDate 하나
좋음: date-utils.ts (40줄) → Claude가 다 읽음 → 전부 관련 있음
```

Claude는 사람처럼 스크롤하며 훑지 않습니다. Read로 파일을 읽으면 전체가 컨텍스트에 들어갑니다. 800줄 파일에서 10줄만 필요해도 800줄이 토큰을 소비합니다.

### 3. Predictability — 하나를 보면 나머지를 추론할 수 있는가?

```
나쁨: routes/users.ts    → express 스타일
      routes/products.js → koa 스타일
      routes/Orders.tsx  → 다른 컨벤션

좋음: routes/users.ts    → 동일 패턴
      routes/products.ts → 동일 패턴
      routes/orders.ts   → 동일 패턴
```

패턴이 일관되면 Claude는 하나만 읽고 나머지를 만들 수 있습니다. 불일관하면 확인을 위해 여러 파일을 더 읽어야 합니다. 더 읽을수록 컨텍스트 오염이 증가합니다.

### 4. Self-documentation — 프로젝트가 스스로를 설명하는가?

사람 개발자는 기억이 있습니다. 온보딩 때 배운 것을 수 년간 기억합니다.
Claude는 매 세션이 첫 날입니다. CLAUDE.md가 유일한 "기억"입니다.

효과적인 CLAUDE.md:
- 아키텍처 지도 (뭐가 어디에 있는지)
- 패턴 사전 (이 프로젝트에서 X를 할 때 Y 방식)
- 규칙 (하지 말아야 할 것)
- 실행 방법 (빌드, 테스트, 린트)

이게 없으면 Claude는 이 모든 것을 매 세션마다 탐색으로 재발견해야 합니다.

### 5. Isolation — 변경 범위가 자연스럽게 한정되는가?

```
나쁨: 인증 수정하려면 → 10개 파일을 읽어야 전체 그림이 보임
좋음: 인증 수정하려면 → src/auth/ 안의 3개 파일이면 충분
```

모듈 경계가 명확하면 Claude는 해당 범위만 읽습니다. 경계가 불명확하면 "혹시 여기도?" 하며 점점 더 많은 파일을 읽고, 컨텍스트가 불어납니다.

## "클린 코드"와의 차이

겹치는 부분이 많지만, Claude 특유의 차이점이 있습니다:

| 차원 | 사람 개발자 | Claude Code |
|------|-----------|-------------|
| 기억 | 세션 간 기억 유지 | 매 세션 = 첫 날 (CLAUDE.md 필수) |
| 파일 읽기 | 스크롤하며 훑기 | 전체를 컨텍스트에 로드 (크기 = 비용) |
| 네비게이션 | IDE의 Go to Definition | Grep/Glob 검색 (이름 = 발견 가능성) |
| 패턴 학습 | 코드베이스와 오래 함께함 | 지금 읽은 것에서만 추론 (일관성 = 효율) |
| 범위 파악 | 경험적으로 앎 | 명시적 경계 없으면 과도하게 탐색 |

---

## 그래서 플러그인이 해결해야 할 문제

정리하면, 좋은 컨텍스트 엔지니어링이 된 프로젝트란:

> **Claude Code가 코딩할 때, 최소한의 탐색으로 최대한의 정확한 컨텍스트를 확보하여, 토큰 예산의 대부분을 탐색이 아닌 실제 코딩에 쓸 수 있는 프로젝트**

5가지 차원으로 분해하면:

| # | 차원 | 핵심 질문 | 나쁠 때의 비용 |
|---|------|----------|--------------|
| 1 | Navigability | 찾을 수 있는가? | grep/glob 반복 → 검색 결과 누적 |
| 2 | Readability | 읽었을 때 신호가 높은가? | 큰 파일 읽기 → 잡음 토큰 축적 |
| 3 | Predictability | 하나로 나머지를 추론 가능한가? | 확인 읽기 반복 → 중복 컨텍스트 |
| 4 | Self-documentation | 스스로 설명하는가? | 매 세션 재탐색 → tokens-per-task 폭증 |
| 5 | Isolation | 범위가 한정되는가? | 과도한 탐색 → 컨텍스트 오염 |

이 5가지가 플러그인의 **문제 공간(problem space)** 이 됩니다.
