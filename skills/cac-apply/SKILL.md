# Apply Suggestion

Review and apply pending structural suggestions and hygiene issues generated by Auto Context.

## Arguments

- No argument: list all pending items, ask user to select
- `{timestamp}`: apply specific item by timestamp ID (e.g., `/cac-apply 20260323-143052`)
- `all`: ask user "몇 개를 적용하시겠습니까?" then apply that many sequentially

## Procedure

### Step 1: Scan pending items

1. Read all `.md` files in BOTH directories:
   - `.claude-auto-context/suggestions/`
   - `.claude-auto-context/hygiene/`
2. For each file, check status by looking for a line matching exactly `^applied$`, `^rejected$`, or `^failed$` (bare word on its own line — NOT substring match)
3. Files without any of these status words are pending

### Step 2: No argument — interactive selection

1. Display numbered list of all pending items (timestamp ID + title + source directory)
2. If 0 pending: output "대기 중인 suggestion/hygiene이 없습니다." and stop
3. Ask user to select which item(s) to apply

### Step 3: `all` argument — count selection

1. Count total pending items
2. Ask user: "총 {N}건 대기 중. 몇 개를 적용하시겠습니까? (1-{N})"
3. Apply the selected count sequentially, stopping on first failure

### Step 4: Apply selected item

For each selected item, follow this exact sequence:

#### 4a. Read suggestion file
Read the full `.md` file to understand the proposal.

#### 4b. Mandatory read-first gate
Read EVERY file listed in `## Related Files` section. This is non-skippable — even if you think you know the file contents, read them to establish ground truth.

#### 4c. Parse and execute Proposal
Check if `## Proposal` contains structured subsections:

**If structured format (has `### Files to modify`):**
1. Parse `### Files to modify` for the target file list
2. Parse `### Changes` for the ordered change list
3. Execute each change in order
4. After all changes, verify against `### Acceptance criteria` checkboxes

**If legacy format (free-form `## Proposal` without subsections):**
1. Read the proposal text carefully
2. If the proposal is ambiguous or unclear, ask the user for clarification — do NOT guess
3. Execute the changes described
4. Verify the changes match the `## Problem` description

#### 4d. Run test runner
1. Check if `package.json` exists at project root
2. If yes, read it and check `scripts.test` field
3. If `scripts.test` exists AND its value is NOT `"echo \"Error: no test specified\" && exit 1"` (npm default stub), run: `npm test` (or `bun test` if bun.lockb exists)
4. If no package.json or no test script: skip testing, log "no test runner detected"

#### 4e. Update suggestion status
Find the existing `## Status` line in the file. Replace the ENTIRE status block using this logic:

1. Remove ALL existing lines matching: `## Status`, `applied`, `rejected`, `failed`, `pending`, `## Applied At`, `## Changes Made` and any content between them
2. Append a single clean status block at the END of the file:

```
## Status
applied

## Applied At
{ISO 8601 timestamp}

## Changes Made
- {file}: {description of change}
- {file}: {description of change}
```

IMPORTANT: Use replacement, not append. The file must contain exactly ONE `## Status` section after update.

#### 4f. Report summary
Output what was changed: files modified, lines added/removed, test result.

## Error Handling

- If suggestion references files that don't exist: skip with warning, do NOT mark as failed
- If tests fail after applying changes:
  1. Revert ALL changes made in step 4c (use git checkout or re-read originals)
  2. Mark suggestion status as `failed` (not `applied`)
  3. Report which test failed and why
- If Proposal is ambiguous (legacy format without structured subsections): ask user for clarification, do NOT guess
- If a file in `## Related Files` doesn't exist: warn but continue (the suggestion may be about creating it)

## Anti-Patterns

- Do NOT apply without reading the full suggestion first
- Do NOT skip the read-first gate (reading Related Files)
- Do NOT skip test verification if a test runner is detected
- Do NOT modify the suggestion's Problem/Evidence sections
- Do NOT apply a suggestion that is already `applied`, `rejected`, or `failed`
- Do NOT append status — always replace to prevent duplicate ## Status blocks
