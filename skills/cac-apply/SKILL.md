# Apply Suggestion — Safe Refactoring Workflow

Review and apply pending structural suggestions and hygiene issues generated by Auto Context.
This skill operates as a CTO-level refactoring engineer: read everything first, checkpoint before touching code, change one thing at a time, verify after every change, rollback on failure.

## Arguments

- No argument: list all pending items, ask user to select
- `{timestamp}`: apply specific item by timestamp ID (e.g., `/cac-apply 20260323-143052`)
- `all`: ask user "몇 개를 적용하시겠습니까?" then apply that many sequentially

---

## Phase 0: Safety Pre-checks

Before doing ANYTHING, verify the environment is safe for refactoring.

### 0a. Dirty tree guard

```bash
DIRTY=$(git status --porcelain 2>/dev/null | head -1)
```

If output is non-empty:
- Report: "uncommitted changes가 있습니다. 리팩토링 전에 커밋 또는 stash 하세요."
- Ask user: `A) git stash 후 진행` / `B) 현재 상태에서 진행 (위험)` / `C) 취소`
- If B: warn "테스트 실패 시 롤백이 다른 변경까지 되돌릴 수 있습니다" and proceed
- If C: stop

### 0b. Test runner detection

```bash
[ -f package.json ] && cat package.json | grep -q '"test"' && echo "HAS_TESTS" || echo "NO_TESTS"
```

Record `HAS_TESTS` or `NO_TESTS` for later use. If tests exist, verify they pass BEFORE any changes:

```bash
npm test 2>&1 || bun test 2>&1
```

If tests already fail: report "기존 테스트가 이미 실패합니다. 리팩토링 결과 검증이 불가능합니다." Ask user whether to proceed anyway. Record failing test names as `PRE_EXISTING_FAILURES` — these are not caused by the refactoring.

### 0c. Checkpoint creation

Create a lightweight checkpoint so rollback is always possible:

```bash
CHECKPOINT_SHA=$(git rev-parse HEAD)
CHECKPOINT_BRANCH=$(git branch --show-current)
```

Report: "체크포인트: `{CHECKPOINT_SHA}` (현재 HEAD). 문제 발생 시 여기로 롤백합니다."

## Phase 1: Scan Pending Items

### 1a. Read all pending items

1. Read all `.md` files in BOTH directories:
   - `.claude-auto-context/suggestions/`
   - `.claude-auto-context/hygiene/`
2. For each file, check status by looking for a line matching exactly `^applied$`, `^rejected$`, or `^failed$` (bare word on its own line — NOT substring match)
3. Files without any of these status words are pending

### 1b. No argument — interactive selection

1. Display numbered list of all pending items with metadata:
   ```
   #  | Timestamp       | Title                              | Category              | Complexity
   1  | 20260404-045246 | Split StyleControls.tsx             | ai-unfriendly-large   | HIGH (9 files)
   2  | 20260404-050020 | Embedded override scattered files   | ai-unfriendly-struct  | LOW (docs only)
   ```
2. Complexity is derived from `### Files to modify` count: 1 file = LOW, 2-3 = MEDIUM, 4+ = HIGH
3. If 0 pending: output "대기 중인 suggestion/hygiene이 없습니다." and stop
4. Ask user to select which item(s) to apply
5. **Recommend starting with LOW complexity items** — they build confidence and catch format issues early

### 1c. `all` argument — count selection

1. Count total pending items
2. Ask user: "총 {N}건 대기 중. 몇 개를 적용하시겠습니까? (1-{N})"
3. Apply the selected count sequentially, **sorted by complexity ascending** (LOW → MEDIUM → HIGH)
4. Stop on first failure

## Phase 2: Understand the Suggestion (READ ONLY — no edits yet)

For each selected item:

### 2a. Read suggestion file

Read the full `.md` file. Extract:
- `## Problem` — what's wrong and why
- `## Related Files` — every file involved
- `## Proposal` — what to change
- `### Files to modify` — target list (if present)
- `### Changes` — ordered change list (if present)
- `### Acceptance criteria` — verification checkboxes (if present)

### 2b. Format validation gate

Check if the suggestion has the structured format:

| Has `### Files to modify`? | Has `### Changes`? | Has `### Acceptance criteria`? | Format | Action |
|---|---|---|---|---|
| YES | YES | YES | **Structured** | Proceed normally |
| YES | YES | NO | **Partial** | Proceed, but derive acceptance criteria from Problem description |
| NO | NO | NO | **Legacy** | STOP. Report: "이 suggestion은 legacy 포맷입니다. 구조화된 변경 계획 없이 대규모 리팩토링은 위험합니다." Ask user: `A) 구조화 포맷으로 변환 후 진행` / `B) 그대로 진행 (위험)` / `C) 스킵` |

If A: rewrite the suggestion's Proposal section into structured format (Files to modify + Changes + Acceptance criteria) and save to the suggestion file before proceeding.

### 2c. Mandatory read-first gate

Read EVERY file listed in `## Related Files` section. This is **non-skippable** — even if you think you know the file contents, read them to establish ground truth.

After reading, report a one-line summary per file:
```
파일 확인 완료:
  - StyleControls.tsx (1080줄, PropertyPanel 하위)
  - PropertyPanel.tsx (240줄, StyleControls 임포트)
  - CardInfoSection.tsx (85줄, 분할 모델 참고)
```

If any file in Related Files doesn't exist: warn "파일 없음: {path}" but continue (the suggestion may be about creating it).

### 2d. Impact assessment

Before making any changes, assess and report:

1. **Scope**: "이 변경은 {N}개 파일을 수정하고 {M}개 파일을 생성합니다."
2. **Risk level**:
   - LOW: 문서 변경만 (CLAUDE.md, rules, comments)
   - MEDIUM: 리팩토링 (기존 코드 이동/분할, 기능 변경 없음)
   - HIGH: 구조 변경 (새 상태 도입, API 변경, 데이터 흐름 변경)
3. **For HIGH risk**: "이 변경은 HIGH 위험도입니다. 별도 브랜치에서 작업을 권장합니다." Ask: `A) 별도 브랜치 생성` / `B) 현재 브랜치에서 진행`

If A: `git checkout -b refactor/{suggestion-timestamp}`

## Phase 3: Execute Changes (One at a time)

### 3a. Change execution order

If structured format: follow `### Changes` numbered list in order.
If legacy format (user chose to proceed): derive logical order from Proposal text.

**For each individual change:**

1. **Announce**: "변경 {N}/{total}: {description}"
2. **Execute**: Make the edit
3. **Verify syntax**: Run language-appropriate check
   - TypeScript/JavaScript: `npx tsc --noEmit` on the modified project (if tsconfig.json exists)
   - Shell scripts: `bash -n {file}`
   - JSON: `cat {file} | python3 -m json.tool > /dev/null`
4. **If syntax fails**: Revert this specific change, report error, ask user whether to skip or fix
5. **If syntax passes**: Proceed to next change

### 3b. Atomic commit per logical group

After completing a logical group of changes (e.g., "extract utility functions" = multiple files but one concept):

```bash
git add {changed files}
git commit -m "refactor({scope}): {description}

Applied suggestion {timestamp}: {title}"
```

**Do NOT batch all changes into one commit.** Each commit should be independently revertable.

### 3c. Test after each commit

If `HAS_TESTS`:
```bash
npm test 2>&1 || bun test 2>&1
```

Compare results against `PRE_EXISTING_FAILURES`:
- **New failure** (not in pre-existing list): This commit broke something. Proceed to Phase 4 (Failure Recovery).
- **Same failures as before**: Safe. Continue.
- **Fewer failures**: Even better. Continue.

If `NO_TESTS`: Skip, but report "테스트가 없어서 자동 검증 불가. 수동 확인을 권장합니다."

---

## Phase 4: Failure Recovery

If any test fails after a change:

### 4a. Diagnose

1. Read the failing test to understand what it checks
2. Read the changed code to understand what was modified
3. Determine: is the test failure caused by the refactoring, or is the test itself outdated?

### 4b. Decide

- **Refactoring broke functionality**: Revert the last commit (`git revert HEAD --no-edit`), mark the suggestion as `failed`, report what went wrong
- **Test needs updating** (e.g., test imports from old path after file split): Fix the test as part of the refactoring, re-run, re-commit
- **Unclear**: Ask user. Do NOT guess.

### 4c. Full rollback option

At any point during Phase 3 or 4, if the situation is unrecoverable:

```bash
git reset --hard {CHECKPOINT_SHA}
```

Report: "체크포인트로 롤백했습니다. 모든 변경이 취소되었습니다."
Mark suggestion as `failed`.

---

## Phase 5: Verification & Acceptance

After all changes are committed and tests pass:

### 5a. Acceptance criteria check

If `### Acceptance criteria` exists in the suggestion:
- Go through each checkbox item
- Verify it with actual file reads or command execution
- Report: `[PASS] criteria description` or `[FAIL] criteria description`

If any criteria FAIL: ask user whether to proceed with marking as applied or to fix.

### 5b. Before/after summary

Report a concrete diff summary:

```
=== Suggestion Applied: {title} ===

변경 전:
  - StyleControls.tsx: 1080줄 (1개 파일)

변경 후:
  - StyleControls.tsx: 95줄 (orchestrator)
  - ColorControls.tsx: 120줄
  - TypographyControls.tsx: 85줄
  - ... (9개 파일)

커밋: 3개 (extract utils → extract components → update imports)
테스트: 전체 통과 (기존 실패 0개, 새 실패 0개)
Acceptance criteria: 5/5 PASS
```

### 5c. Update suggestion status

Find the existing `## Status` line in the file. Replace the ENTIRE status block:

1. Remove ALL existing lines matching: `## Status`, `applied`, `rejected`, `failed`, `pending`, `## Applied At`, `## Changes Made` and any content between them
2. Append a single clean status block at the END of the file:

```
## Status
applied

## Applied At
{ISO 8601 timestamp}

## Changes Made
- {file}: {description of change}
- {file}: {description of change}

## Commits
- {sha short}: {commit message}
- {sha short}: {commit message}

## Verification
- Tests: {PASS/SKIP/FAIL}
- Acceptance criteria: {N/M PASS}
- Pre-existing test failures: {count}
```

IMPORTANT: Use replacement, not append. The file must contain exactly ONE `## Status` section after update.

## Phase 6: Next Item or Finish

If applying multiple items:
1. Report completion of current item
2. Ask: "다음 suggestion으로 진행할까요? ({remaining}개 남음)"
3. If yes: return to Phase 2 for the next item
4. If no: proceed to finish

### Finish report

```
=== cac-apply 완료 ===

적용: {N}개
스킵: {M}개
실패: {K}개

커밋 목록:
  - {sha}: {message}
  - {sha}: {message}

롤백 방법: git reset --hard {CHECKPOINT_SHA}
```

## Error Handling

| 상황 | 행동 |
|------|------|
| suggestion이 참조하는 파일 없음 | 경고 출력, 스킵 (failed로 표시하지 않음) |
| 테스트 실패 (리팩토링 원인) | 해당 커밋 revert, suggestion을 `failed`로 표시 |
| 테스트 실패 (테스트 자체 문제) | 테스트도 함께 수정, re-run |
| Proposal이 모호 (legacy 포맷) | 구조화 변환 제안 또는 유저 확인 |
| 파일 분할 후 임포트 깨짐 | 분할 커밋에 임포트 수정을 포함 |
| HIGH 위험 + dirty tree | 강력히 경고, 브랜치 생성 권장 |
| TypeScript 컴파일 에러 | 해당 변경 revert, 에러 보고 |

## Anti-Patterns

- Do NOT apply without reading the full suggestion first
- Do NOT skip the read-first gate (reading Related Files)
- Do NOT skip test verification if a test runner is detected
- Do NOT modify the suggestion's Problem/Evidence sections
- Do NOT apply a suggestion that is already `applied`, `rejected`, or `failed`
- Do NOT append status — always replace to prevent duplicate ## Status blocks
- Do NOT batch all changes into one giant commit — atomic commits per logical group
- Do NOT proceed past a test failure without diagnosing root cause
- Do NOT make functional changes during a refactoring — if the suggestion requires behavior changes, flag it as HIGH risk
- Do NOT leave the working tree dirty after completion — all changes must be committed or reverted

## Escalation

If you've attempted to apply a suggestion 3 times and it keeps failing:

```
STATUS: BLOCKED
REASON: {1-2 sentences}
ATTEMPTED: {what you tried}
SUGGESTION: {what the user should do}
ROLLBACK: git reset --hard {CHECKPOINT_SHA}
```

Stop. Do not retry further.
